The first deliverable is a measurable task

The present harness listens to meeting replay and delivers knowledge cards. The direct-question adapter ends after a single response. Neither yet proves that an employee assessment was saved or an accepted offer was applied. Reuse the event ledger, checkpoints and model/tool logs, then add a shared interactive user and a deterministic business world.

JSON task packs and state tables are experimental infrastructure. The potential research result is a reproducible explanation of which intervention reduces which failure, under what cost and transfer limits.

Coverage is a read-only assessment of existing code and traces, not a new measured result. The full protocol lists local provenance. A correct final artifact can hide earlier loss; a completed run can still contain an unsuccessful task.

Two concrete task settings

Primary task

Automotive employee training

Answer grounded questions, administer a scenario assessment, handle explanations and corrections, then save an evidence-backed evaluation.

Evidence of completion. Separate correct tutoring, independently demonstrated knowledge and a successfully saved assessment. Mark assisted answers; respect withdrawal.

A text assessment is not proof of practical repair skill. New-model vehicle claims require authorized manuals and expert review.

Second domain

Telecom offer and change

Resolve a standard-price request plus implicit loyalty eligibility, explain conditions, obtain acceptance and submit a simulated change.

Evidence of completion. Offer, acceptance, pending change, applied change and delivered confirmation remain separate states.

Use fictional fixed policies and sandbox transactions. No real carrier accounts, payments or email delivery claims.

Keep the task contract separate from the evaluator

  1. Public task packPolicy, knowledge, questionnaire and allowed tools
  2. Interactive userPrivate facts and a fixed disclosure / response policy
  3. Business worldAuthoritative state, revisions and tool receipts
  4. Independent evaluatorHidden gold, process constraints and legitimate endings

The user simulator cannot write the business result. The actor cannot see hidden gold or future user facts. Start with branching scripts, then test another user-generation method and small human anchors. Permit completion, needed information, pause and withdrawal without forcing every conversation through a questionnaire.

A prompt control before an architecture claim

ArmInterventionQuestion
B · Adapted referenceAgent-led / ReAct-style tool choice and free notes; common multi-turn interface.Baseline failure discovery
P · Prompt onlyB plus reminders to maintain multiple needs, apply corrections and use completion evidence.P − B: does a simple prompt suffice?
S · Persistent stateP plus per-need/field state, provenance, revisions and dependency updates.S − P: incremental state-management benefit
V · Completion checkP plus verification of accessible business receipts before claiming completion.V − P: incremental verification benefit
SV · CombinedP plus both state and completion checks.SV − S − V + P: interaction

P / S / V / SV form the 2 × 2 comparison; B measures the effect of the prompt itself. Use the same model, public rules, tool access, context and resource caps. Pair initial scenarios and user conditions, not supposedly identical subsequent dialogue.

These are initially package effects. If state helps, compare it with a free-text summary at the same update frequency and token allowance. If verification helps, compare it with an ordinary reviewer at the same budget. Keep permissions and legal commit prerequisites identical across arms. Verification uses accessible receipts, never hidden evaluation answers.

Score decisions as well as outcomes

The primary measure is whole-task success for all trajectories assigned in advance to executable, expected-completion cases: all current requirements, valid process, correct business state and truthful delivery. Agent-induced withdrawal remains incomplete in that denominator. Also report legitimate-ending compliance, per-field correctness, H1–H4, recovery, stale-state duration, unnecessary questions and full cost. Report attempted false claims, delivered false claims and false blocks separately.

Use blinded ratings and deterministic state assertions; audit all unsupported completion claims and arm-discordant outcomes. Report paired differences and uncertainty clustered by task family. Repeated runs do not increase the number of task families. These designed families do not guarantee sampling independence.

Run in stages, with an early stopping point

PLANNED · 48 RUNS

Discover failures first

24 cases × 1 arm(s) × 1 model(s) × 2 repeats

Six development task families, four conditions each. Review failures before building a candidate mechanism.

PLANNED · 480 RUNS

Compare only justified changes

24 cases × 5 arm(s) × 2 model(s) × 2 repeats

Full design ceiling, including the 48 discovery runs only if every frozen condition matches. Six families remain six clustering units; omit factorial claims if a mechanism branch is stopped.

PLANNED · 192 RUNS

Freeze, then test transfer

24 cases × 2 arm(s) × 2 model(s) × 2 repeats

Twelve new families with two conditions each. Compare P with one common candidate selected before testing. Freeze prompts, schema, code and grading. Cross-domain claims require a new domain.

These are planning ceilings, not results or a power calculation. Reusing discovery gives 672 total planned runs through transfer; otherwise 720. Engineering checks, oracle branches and extra ablations are outside these totals. Development has only six task families. Estimate real machine cost after a small pilot; do not launch the full grid before understanding its failures. Keep all variants of a family in one split.

Before model runs: obtain suitable source material, review case gold with domain expertise, manually walk success and failure/withdrawal branches, and freeze code, model digests, tasks, grader and budgets. Questionnaire transfer within a domain and transfer to a new domain must be reported separately.

Test asynchronous scheduling later

First compare blocking on tool results with handling independent work while a tool is pending. Keep one actor-model request in flight in both arms. Concurrent LLM workers and full-duplex speech are separate factors.

Freeze joint tool-delay and event-generation rules, dependencies and budgets. Equal inputs and world state produce equal results; fix query snapshot timing and simultaneous-event ordering. Include a correction arriving before a stale result, withdrawal, retries and duplicate submissions. First validate semantics on a replayable clock; then measure real wall time under matched hardware and load. Simulated 250 ms model latency cannot establish real speed.

A faster first reply with more stale commits is a tradeoff, not an unqualified improvement. Do not prescribe asynchronous execution before observing a relevant bottleneck.

Human language, expert criteria, independent gold

Use human dialogue as language evidence, occupational sources as rubric inputs, and separately reviewed task assertions as gold. Do not label researcher or model extensions as original human dialogue. ReAct already supports plan updates; τ and ARE already provide relevant task and event infrastructure.

  • Taskmaster-1 · official data ↗

    Select two-person automotive WoZ dialogue for human language; retain source IDs and attribution. Role-play, not naturally occurring company calls. The corpus also contains self-written dialogue. CC BY 4.0; automotive subset not yet extracted.

  • ASE Automobile 2026 · official guide ↗

    Expert task coverage and knowledge-assessment forms. Public access does not authorize republishing the question bank; not a new-vehicle manual or dialogue gold.

  • AURACA101 · official competency standard ↗

    Requirements clarification, outstanding needs and follow-up as rubric inputs. A competency standard is not a ready-made questionnaire. Redistribution terms have not been verified.

  • ReAct · original paper ↗

    Interleaved reasoning and acting as a reference strategy. ReAct does not require the agent to track only one intention; structural failure must be measured.

  • τ²-bench · versioned paper ↗

    Separate policy, private user task, tools and terminal assertions. The official repository has evolved to τ³. Pin code, tasks and grader; do not compare unversioned scores.

  • Gaia2 / ARE · versioned paper ↗

    Dynamic events, dependencies and asynchronous environments. An asynchronous environment or parallel tools do not imply universal gains.

  • Mind the Sim2Real Gap · versioned paper ↗

    Motivates independent checks of simulated-user behavior and human anchors. Simulation outcomes cannot by themselves establish real-user benefit.

  • FormBharo · versioned paper ↗

    Related work on extraction plus deterministic form-state handling. Limited form and simulator coverage; per-field correctness is not whole-task success or arbitrary-JSON transfer.

What remains unproven

  • No new model experiments, human study, clinical task or architecture implementation in this update.
  • The 48 / 480 / 192 counts are staged planning ceilings, not completed runs or power guarantees. Extra oracle and ablation runs are not included.
  • Expert-reviewed cases, executable gold and a shared interactive business adapter remain to be built.
  • State and verification arms initially estimate intervention-package effects, including computation. Matched-budget summary/reviewer controls are required for narrower mechanism claims.
  • A questionnaire can change through JSON only within a shared schema and operation set; new business operations require an adapter.
  • Previous research findings and frozen baselines are unchanged.
