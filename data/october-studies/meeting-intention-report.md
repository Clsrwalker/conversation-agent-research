# 常见会议场景：现有旁听基线的测试结果

2026-10-16。网站未更新。

**三类会议各跑了两遍。六次都没有在结束时保留完整、适用的帮助。** 五次结束时没有卡片；另一次留着开头的通用说明，没有随个人条件和取消信息更新。

这批测试已经找到具体失败位置，可以据此选择下一个编排实验。它还没有证明某种新编排会更好。

## 测了什么

使用原有冻结的旁听 baseline（`2026-10-07-agent-led-recovery-v1`），让同一个本地 Qwen 2.5 14B 处理三段会议。每段有三个人、九轮发言，包含插话、补充问题和条件变化。

| 会议 | 需要提供的帮助 | 实际表现 |
| --- | --- | --- |
| 团队讨论外出记录工具 | 解释离线编辑、同步和 PDF 限制；Android 改成 iPhone 后更新答案 | 一遍只在文字里写发布代码，没有执行。另一遍先发布成功，后来撤回旧卡片，替换失败后没有恢复。两遍结束时均为空。 |
| 研究组讨论实验结果 | 区分回归测试和独立评估，解释调过 prompt 的旧案例能证明什么，再回答重复运行的问题 | 两遍都没有检索或发布。模型在内部直接接话，部分解释还引入了对话里没有的新评估条件。 |
| 志愿者讨论工作坊安排 | 分清两个人各自的培训和预约；Mira 取消修灯，Owen 的修凳子需求继续 | 一遍只生成内部回复。另一遍早早发布通用规则，此后没有更新，也没有清除取消任务的旧表述。 |

这些是新编写的、接近日常会议形式的文字稿，配有七份虚构资料。不是录音、真实 ASR 或真实用户研究。人名和产品规则都是测试设定。所有场景都需要一定的帮助，因此不能用这批数据估计一般会议中的打扰率。

## 最值得看的两条轨迹

### 文字中的工具调用没有执行

团队会议第二遍中，模型反复在普通回复里写 `publish_card(...)`。但实际 `tool_calls` 和工具记录中没有对应发布，用户始终看不到卡片。检索和读取工具确实执行过，因此不能笼统地说本地模型完全不会调用工具。

后来 iPhone 改口也进入了模型输入。它在内部回应了新设备的限制，但仍没有真正发布。普通回复不显示，是这套冻结旁听基线原有的接口约定；网页的单问题测试采用另一种输出适配，不能把两者混为一谈。

### 旧卡片撤掉了，替换没有成功

团队会议第一遍发生了更完整的失败链：

| 回放时间 | 实际发生的事 |
| --- | --- |
| 3.750 秒 | 成功显示 Android 离线编辑的正确答案。 |
| 4.500 秒 | 同一批工具动作先撤回旧卡片，再尝试重新发布；撤回成功，替换返回 `conflict`，当前卡片为空。 |
| 下一次调用 | 模型已经收到失败回执，却在内部说卡片已更新、没有冲突。它又写出发布代码，但没有真正调用发布工具。 |
| 52 秒 | 用户改用 iPhone，这条变化也进入模型输入。后面没有成功发布新答案。 |
| 120 秒截止 | 没有任何活动卡片。 |

这里并不是知识答案从未生成，也不是改口没有送达。先前正确的帮助只显示了 0.750 个模拟秒，随后被撤掉，失败回执又没有带来有效的继续执行。

工作坊第一遍还暴露出另一种情况：早期通用卡片一直保留，模型后面仍在内部回复，却不更新用户看到的内容。内部回复中甚至出现“得到许可后可以使用 Mira 的预约”的建议，与资料明确规定的不可共享、不可转让冲突。这些错误没有发布给用户，不能计作已经展示的错误；但它们说明直接显示所有内部文字并不能解决问题。

## 结果怎样计算

每场在 120 秒模拟截止时检查当前卡片，要求覆盖该场三个必要结论，并适用于最新的人物、设备和任务范围。正确的早期卡片另行保留记录，不会因为后来失败就当作从未出现。

两份独立 AI 评分一致判定：**完整帮助为 0/6**。这不是人工评分，也不是“模型六次什么都不懂”。逐项看，18 个结论机会中，1 项满足、16 项遗漏、1 项有评分边界：通用的“每个人必须有自己的预约”是否已经充分表达“取消别人的预约不会转给你”。两种判定都不改变完整帮助为零的结果。

保留的通用卡片仍提及已取消的修灯任务。两位评分者对是否同时将它记为实质错误有不同意见，已在裁定记录中保留；最终帮助不完整并不依赖这项争议。公开显示的旧内容、未显示的内部错误、没有交付的正确解释，分开记录。

六次均正常运行到回放窗口结束，所有 54 轮发言都实际进入模型输入，没有预算耗尽或失败的模型调用。因而这批失败不能归因于预算在关键改口前就用完了。工具层存在上述一次替换冲突。

## 下一步改哪里

**先比较交付和更新失败后的继续执行方式。** 原流程保留为对照；实验版本在普通回复结束或发布失败后，更明确地反馈当前真正显示的内容和上次发布结果，让 agent 决定发布、重新调查、更新或保持安静。

这些状态在原日志里已经存在；要测试的是模型何时看到它们、一次未完成的交付怎样回到执行循环，而不是声称增加了模型原本完全拿不到的信息。只改这一处，保持模型、输入、工具和资源限制相同，并保留取消及已解决问题的测试，检查漏答减少时是否增加错误或无益发布。

概念会议中“没有查询资料”是另一个问题，应单独比较检索引导。两项一起改，即使结果变好也难以判断是哪项起作用。暂时没有必要从这六次结果推导出完整的多角色或多类别 harness 设计。

本轮完成的是定位和测试材料；尚未实施上述优化，也没有报告优化收益。

## 耗时和记录

77 次本地模型调用：输入 413,154 tokens，输出 14,132 tokens，总计 427,286。累计模型调用耗时 261.684 秒；每场中位数 40.377 秒，范围 32.230–58.789 秒。这里统计的是实测模型调用时间，不是整套应用耗时，也不是用户说完话后等答案的时间。120 秒是回放时钟。没有付费模型 API 调用。

模型为 `qwen2.5:14b-instruct` Q4_K_M，Ollama 0.40.4；每场最多 24 次调用、软上限 120,000 tokens、每次输出最多 1,200 tokens，温度 0，context 16,384。原冻结代码和资料哈希在测试后仍然匹配。历史基线使用较旧 Ollama，不能把这批结果与旧分数当成完全相同运行环境的复现。
