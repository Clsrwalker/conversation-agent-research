# 普通回答交付：meeting 对照实验

2026 年 10 月 17 日。网站未更新；全部 acting-model 推理在本机完成，没有调用付费 API。

**交付通道已经修通，漏答有所减少，但新配置还不能替换 baseline。** 完整帮助从 0/6 变为 1/6，另有一次结果不确定；同时出现了更多可见错误、重复更新和预算退出。

## 修了什么

原流程只有调用 `publish_card` 才会把内容送到屏幕。调查模型即使已经写出回答，普通正文也可能留在内部，随后继续等待下一段对话。

新增配置 `agent-led-answer-delivery` 在调查结束后增加一个交付步骤。同一个模型读取候选回答、当时已经到达的对话、检索资料和当前卡片，选择发布、更新、撤回或保持不变。调查模型仍可自由作答，文字中的工具调用不会被程序当成代码执行。

交付决定先保存，再通过原有卡片接口提交。中断后复用已保存的决定；新对话和并发修改仍可阻止旧内容覆盖当前卡片。交付审查占用原有调用与 token 预算。原 agent 的直接发布工具继续可用，所以新增步骤并没有统一审核所有输出，也不能保证事实正确。

这项干预同时改变了内容选择、上下文整理和文字表达，实验不能把差异只归因于“把同一句话送到屏幕”。它没有加入正确意图提示、参考答案、新资料或更强的模型。

## 怎样比较

同期重跑 `agent-led-recovery` baseline 和新配置。三个场景分别是手机应用选择、实验结果讨论和志愿者安排，每组每个场景重复两次，共 12 次。输入包含多人需求、设备改口、部分取消和无关话题。资料为封闭的虚构文档。

两组共用本地 Qwen2.5 14B Instruct、16K 上下文、24 次调用上限、120,000 token 软上限及原检索工具。顺序交替，串行运行；没有选择性重跑。每次评分只看固定截止时仍可见的卡片，每个必要结论最多计一次；内部回答不计帮助。早期错误单独保留。

三类场景和评分标准均沿用冻结的 `meeting-intention-v1`。它们是开发场景，不是留出测试、真实 ASR 或用户研究。每个场景都需要某种帮助，因此不能据此估计普通会议中的误打扰率。两次重复也不等于两个独立场景。

## 帮助质量

| 截止时的实际输出 | Baseline | 新交付配置 |
| --- | ---: | ---: |
| 明确完整解决全部需求 | 0/6 | 1/6 |
| 完整帮助判定不确定 | 0/6 | 1/6 |
| 明确满足的必要结论 | 0/18 | 6/18 |
| 不确定的必要结论 | 0/18 | 2/18 |
| 最终卡片有明确实质错误 | 0/6 | 3/6，另 1 次不确定 |
| 过程中曾有明确实质错误 | 0/6 | 4/6，另 2 次不确定 |
| 最终仍有过时建议 | 0/6 | 1/6 |

Baseline 六次运行在截止时都没有卡片。它曾发布一次正确的 Android 帮助，但在设备变化前就撤回了。因此，零可见错误不能理解为 baseline 已经提供了可靠帮助。

两份独立、匿名的 AI 评审对全部 12 次的成功／不成功标签及 36 项需求标签一致；若同时要求主结果的不确定性标记一致，则为 11/12。共有 5 处评分字段分歧，主要涉及不确定性和中途错误。根 agent 对原始事件作了非盲裁决；两份原评审和裁决均保留。这不是人工标注。未能确定的项不计入明确成功，且没有为了提高成功率修改原标准。

| 场景 | Baseline，两次 | 新配置，两次 |
| --- | --- | --- |
| 志愿者安排 | 都未展示最终帮助 | 一次完整成功；另一次满足个人资格和不可转让条件，但培训名额的条件表达不确定 |
| 手机应用选择 | 都没有最终卡片 | 一次仍保留过时的 Android 建议；另一次回答了部分 iPhone 限制，但未补齐三项必要结论 |
| 实验结果讨论 | 都未展示最终帮助 | 两次都展示了错误解释，未正确区分回归检查与独立评估 |

志愿者的明确成功案例中，Owen 收到了自己需要培训和预约、不能沿用 Mira 的资格、周日安排取决于名额的帮助。Mira 取消灯具维修后，卡片把她的维修部分改为已取消，同时保留 Owen 的需求。这是本轮实际观察到的有效交付。

两个保留的不确定需求分别是培训名额的条件表达，以及被截断的 PDF 摘录能否支持密码保护结论。PDF 那次即使按有利方向判定，仍因过时的 Android 建议而不能算完整成功。

## 还没解决什么

**交付检查会继承错误。** 首个实验讨论案例没有搜索或读取资料。最早的错误由调查 agent 直接发布，交付步骤随后继续保留；后来候选回答已不含该错误，它仍从旧卡片中被重新带回。增加一次同模型检查，没有解决证据不足和旧内容污染。

**改口后追加新句子不等于修正旧结论。** 一次手机场景在 iPhone 变化后补上了新说明，却仍把 Android 离线编辑建议留作当前内容。状态版本检查能阻止已经过期的提交，不能判断一张新提交的卡片里是否还混有旧建议。

**展示过于频繁。** 新组六次都有不必要的重复修订。47 次交付审查最终产生 37 次实际发布或更新，另有 5 次提交内容不变、1 次被新输入阻止；原 agent 直接产生了另外 6 次发布或更新。43 个显示事件只对应 6 项明确满足的最终结论。

因此，本轮保留新配置供实验使用，不把它升为默认。下一步值得优化的是：更新前重新检查每个结论是否仍适用、是否有足够证据，并减少没有新增帮助的审查和重写。仅继续提醒模型“记得展示”不足以解决这些问题。

## 执行成本

| 六次运行合计，或注明的平均值 | Baseline | 新交付配置 |
| --- | ---: | ---: |
| 模型调用 | 76 | 129 |
| 其中交付审查 | 0 | 47 |
| 总 token | 409,555 | 573,428 |
| 每个场景平均累计模型耗时 | 42.4 秒 | 78.5 秒 |
| 实际发布或更新事件 | 1 | 43 |
| 因预算提前结束 | 0/6 | 3/6 |

新组 token 增加 40.0%，累计模型耗时增加 85.0%。耗时是场景内所有模型调用的实测总和，不是单条答案延迟；对话和工具到达时间采用模拟时钟。卡片事件数包含更新，不能当作解决问题的数量。

两个手机场景用完 24 次调用后结束。另一场志愿者运行在一次调用后达到 126,804 token，超过软上限 6,804；下一次调查被 `BudgetExceeded` 阻止，原运行保留为 `error`。它没有重跑，也没有被审计报告改记为成功。截止时已有卡片仍按原评分规则评价。

## 验证与记录

新增 20 项交付集成测试和 114 项相关回归测试通过。冻结的实验源码另通过 21 项交付与捕获测试；这些是对其中测试的复验，不额外算作新测试。离线检查覆盖实际 LangGraph 与 SQLite、共享预算、新输入、并发卡片更新以及中断恢复，不能代替模型质量评估。

12 次运行均通过记录审计。205 次实际模型调用完整保存并入账，共 982,983 token。48 个候选全部对应真实调查模型回应，其中 47 个进入审查；候选对话与证据均没有超出当时的观察范围。冻结源码、baseline 和测试材料哈希核验通过。
