# 会议中的需求识别测试

**已经用三个常见 meeting 场景跑了本地对照。提醒模型注意人物、状态和依据，在部分片段上有帮助，但仍会漏需求和误解取消范围。暂不改生产编排，网站未更新。**

场景分别是外出活动讨论、实验室结果讨论和志愿者安排。每个场景选几个时点，只给模型看此前已经发生的对话，共八个累计前缀。使用同一个本地 Qwen2.5 14B，两组各调用八次：普通提示直接找当前需要的信息帮助；另一组额外提醒注意谁的需求、是否变化或结束、原话依据及不确定性。两组都用自然语言输出，没有强制 JSON。

## 测出了什么

| 会议片段 | 普通提示 | 加入归属和状态提醒 |
| --- | --- | --- |
| 外出讨论：闲聊后仍有三个应用问题 | 通过 | 漏掉离线编辑问题 |
| 本人从 Android 改用 iPhone | 漏掉独立编辑问题 | 通过 |
| 旁人提到兄弟的 Android | 编辑需求是否保留不确定 | 漏掉离线编辑问题 |
| 实验室会议刚提出议程，尚无具体疑问 | 从议程新增了需求 | 正确判断暂无具体需求 |
| 回归结果、调过 prompt 的旧题、重复测试 | 通过 | 通过 |
| 两位志愿者各自询问准入条件 | 漏掉 Mira 自己的问题 | 保留两人的问题 |
| Mira 取消修灯，Owen 仍要修凳子 | 共享预约问题是否过时不确定 | 错把取消范围扩到接待台 |
| 随后有人提到接待台和围裙 | 给 Owen 编造其他志愿任务 | 通过预设项，仍有旧预约表述的歧义 |

按预设检查项，普通提示 **2/8 通过、4/8 失败、2/8 不确定**；加入提醒后 **5/8 通过、3/8 失败**。“通过”指通过本轮检查，不等于文字绝无歧义。最后一个修改组输出仍引用了早先的共享预约疑问，评审保留了这项附加问题。

两名独立匿名 AI 评审对 56 项判断中的 55 项一致。唯一分歧是取消后继续问“一份预约能否供多人使用”：可能是过时需求，也可能是想继续弄清一般准入规则，复核保留不确定。这些评分不是人工金标准。

## 一个清楚的失败案例

Mira 说：“邻居已经修好灯了，我取消了工位预约。我可以去接待台，这个时段已经和 Jo 商量好了。”

正确解释应是：Mira 的修灯问题结束；接待台安排已经确定；Owen 的凳子和自己的准入问题仍未解决。

加入状态提醒后，模型却说 Mira 因取消而不能做接待台，需要重新找人。它还保留了 Owen 使用 Mira 已取消预约的选项。**识别出了“取消”这个动作，却没有正确绑定它取消的对象。** 这比笼统地说“模型忘记意图”更具体，也值得做下一轮诊断。

另一类错误是把两个问题混成一个：“我能不能离线编辑？”与“我的修改能不能同步到同事设备？”并不相同。模型有时只留下同步问题，把离线编辑当成已经成立的前提。多写几句状态提醒没有稳定解决这个问题。

## 与完整 harness 的区别

这次只判断会议中的信息需要，不检索、不发布卡片、不判断实际任务完成。模型每次都重新看到完整前缀，因此不是持久记忆实验。八个前缀来自三个已用于开发的虚构会议，也不是八场独立真人会议或真实 ASR 测试。

已有端到端对照中，完整帮助仍是 **0/6 对 0/6**；那里的失败包括不检索、未实际发卡和预算退出。不能用本轮的识别分数替换那些结果。[完整 harness 对照](../delivery-recovery/RESULTS.md)

16 次请求全部正常结束，无截断，共 6,936 tokens，没有付费 API。单次调用墙钟中位数为 1.43 秒和 1.16 秒；普通组第一次另含约 4.49 秒模型载入。这里只生成短需求说明，不能据此宣布解决了原先三十多秒的完整流程耗时。

## 接下来值得验证的变化

下一轮可先拿“局部取消”和“编辑与同步分离”两个失败做辅助对照：给原 harness 补一份正确的当前需求摘要，保持相同对话、工具和剩余预算，观察调查及交付是否改善。摘要只包含当时可见的信息，不包含知识答案或未来发言。

如果这种辅助仍不能让用户收到帮助，就继续查行动选择、证据使用和发布路径；如果能改善，再测试模型生成的需求状态是否可靠，并计入生成状态的成本。当前结果不支持直接加一个强制任务清单作为解决方案。
