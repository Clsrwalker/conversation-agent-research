METHOD · SEPARATE AUTHORITY, VIEW AND ACTION

What changed, and how the Actor input is built

Separate what the system knows, what the Actor currently reads, and what the model may request next. Keep original evidence available while making the immediate decision context explicit.

Implementation before and now. This is an architecture comparison, not a measured effectiveness comparison.
ResponsibilityEarlier implementationCurrent implementation
Actor inputFull history plus full source/state structures, with overlapping task and evidence representations.One task/progress view, complete recent exchanges and linked older evidence. Selected raw roles appear once.

Three responsibilities, one authoritative evidence state

  1. 1 · Authoritative evidence

    Keep original user sources, accepted records and revisions. The Observer proposes evidence; native code validates it. The Projector derives applicability and completion eligibility.

  2. 2 · Current reading view

    Rebuild a compact task/progress view and select original dialogue for this Actor call. Include coverage metadata and source pointers. This view owns no facts.

  3. 3 · Model-selected action

    The Actor chooses a reply or a bounded read of original history. A read changes the next input, not the evidence. The model still chooses how to explain, defer, return or end.

The deterministic selection algorithm

The following steps construct an input view. They do not choose an interview question or decide which reply is best.

  1. Derive current task status

    Recompute projection from the authoritative snapshot. Merge each requirement’s contract and current state; retain source coordinates and mark invalidated old values explicitly.

  2. Keep the immediate exchange intact

    Select the latest three user exchanges with their actual preceding assistant questions and following replies. Add any saved read results from this pending user turn.

  3. Follow recorded evidence links

    Find older sources through current records, the previous evidence revision, and current or originally bound prerequisite revisions. This is provenance-based selection, without a semantic relevance model.

  4. Add whole older exchanges within budget

    Consider linked sources from newest to oldest. Add whole exchanges within the extra 6,000-character allowance. Do not include neighboring user turns merely because they are adjacent.

  5. Deduplicate, order and expose gaps

    Emit selected original roles once in chronological order, with visible IDs and omitted ranges. Recent text is never clipped; an explicit read may return one oversized first exchange. Character targets are not total token guarantees.

PROCESS · FOLLOW ONE RECORDED CONTINUATION

From a new user request to a recovered original answer

  1. Original inputReceive user turn

    Retain the original text and source ID.

  2. Model decisionObserve evidence

    The Observer reads the full role history and proposes records.

  3. Native executionCommit and project

    Native checks accept evidence; the Projector recomputes current progress.

  4. Model decisionChoose the next move

    The Actor reads the derived view and selects a response or a history read.

  5. Native executionOptional: read and return

    The native reader supplies original text. The Actor runs again with that text; evidence is unchanged. Default limit: two reads per user turn.

  6. Native executionSave and deliver

    An accepted reply enters the outbox. Output is acknowledged separately; saved reads and replies survive interruption.

CONTEXT ORGANIZATION

Keep the task visible. Let the model ask for the past.

  1. One task viewCombine contract and current projection. Keep source coordinates and explicitly marked invalidated values; omit the full sources map and duplicate record table from compact Actor input.
  2. Complete recent exchangesRetain recent original user messages and their actual assistant questions and replies; emit selected raw roles once in chronological order.
  3. Linked older evidenceUse current sources, prior revisions and dependency relationships to add older exchanges within a character budget. Expose omitted ranges; omission is not evidence of irrelevance.
  4. Model-selected readbackRead user turn IDs, backward pages or literal case-sensitive matches under a per-user read limit. Readback does not write evidence or become a delivered assistant reply.
  5. Same authority and recoveryObserver retains full history. The Evidence Store and Projector semantics stay unchanged. Persist context settings, read results and reply acknowledgments; legacy sessions retain full-context behavior.

The Observer still receives the full role history. The Actor receives one combined task/status view, recent complete exchanges and original dialogue linked to accepted or revised evidence. Coverage metadata identifies omitted history; missing projected evidence is not proof that the user never supplied it.

History access is a read-only model action, not a fixed question scheduler. It can request user-turn IDs, a backward page or a literal search. The result contains original text; no extra model-written summary is introduced. Reads do not change evidence and are not delivered as participant-facing replies.

Default bounds and persistence

Recent exchanges: 3. Additional automatic evidence context: 6,000 characters. Explicit read target: 12,000 characters. At most 2 history reads per user turn, separately bounded from reply attempts.

These are character targets, not token limits. Mandatory recent exchanges and a first oversized whole read can exceed a target. The model can still produce a final reply when its read allowance is exhausted.

Configuration, context hashes, coverage and read events are saved and checked during replay. Old sessions retain their full-context mode. Previously generated replies remain recoverable without another model generation.

Scope, limitations and source binding

Authored structured mission; zero live compiler calls for these demonstrations.

Assistant review of native requests, outputs, source hashes, receipts and exact offline replay; no human preference labels.

  • Each case has five authored/scripted prefix user turns and one real-model continuation; the prefix is not a live model dialogue or a human participant session.
  • The real inference is qwen3.5:9b on the pinned local digest. There is no baseline comparison or general assistance-quality, training, or cost-saving claim.
  • The history read is a broad backward page in this small case, not evidence of optimized search or retrieval precision.
  • No hard total-character or total-token guarantee follows from the context character targets: recent text is complete and an explicitly read first exchange may be oversized.
  • CLI display acknowledgments are recorded and replay-consistent; they are not proof that a human read the output.
  • Quoted text/type/source validation remains mechanical. The two observed responses were reviewed by an assistant, not a blinded human panel.
  • Observer still reads full history, so this change does not bound the whole pipeline's input cost.
  • Older uncommitted facts or intent can be omitted from the first Actor view. Automatic evidence links do not guarantee retention of all relevant semantics; the model must request history when needed.
  • There is no summarizer, embedding retriever, attention replacement or weight update. Whether the model chooses the right explanation, deferral, return or ending remains a policy research question.

Next step: Freeze this harness for meeting-directed work: collect real interview decision points, calibrate human preferences, and only then study local preference learning and full-dialogue behavior.

IMPLEMENTED CAPABILITY

Derived progress. Model-selected conversation.

  1. 1 · Compile the missionThe model rewrites questions as information needs. Native code preserves the explicitly authored answer types, requiredness and conditions.
  2. 2 · Record evidence proposalsAn observation model proposes evidence from delivered user text. Native checks validate IDs, value types, source spans and revision rules before commit.
  3. 3 · Project current progressThe projector derives applicable, blocked, satisfied and invalidated items from one authoritative store. It does not choose the next question.
  4. 4 · Choose the next moveThe conversational model sees the updated mission state and dialogue, then chooses to explain, clarify, follow, defer, revisit, finish or withdraw.

One reply, several facts

A user can volunteer information out of questionnaire order. Several requirements can cite the same delivered reply.

Corrections change eligibility

Changing an upstream answer invalidates dependent records. Old evidence is retained for audit and does not silently reappear as current.

Meaning remains a model judgment

An exact quote and valid type establish provenance and contract shape. They do not establish that the proposed value follows from the quote.

COMPILER SCOPE

Typed source contracts are preserved; meaning still needs review.

The input is a structured questionnaire with explicit answer types and applicability conditions. This version does not infer arbitrary conditions from a PDF or free-form prose. Each source item maps to one information requirement; compound source questions need to be split during authoring.

The model generates declarative information needs. Native assembly retains the original question, answer contract, requiredness and condition references. Copying the original question or returning a question-mark ending fails a basic form check, which does not prove semantic fidelity.

WHAT THIS MILESTONE ESTABLISHES

A working foundation for the next research comparison.

The system connects a versioned questionnaire, evidence-derived progress and model-led conversational decisions. Its next research question is whether this representation helps learning and transfers to unfamiliar questionnaires under information-equivalent controls.

  • Explicit typed questionnaire JSON is supported. Arbitrary PDF/prose ingestion and automatic inference of hidden conditions are not implemented.
  • One source item becomes one information requirement. Splitting compound questions is an ingestion task, not an automatic capability of this version.
  • The source question and native contract remain available. Compiler paraphrases can drift: one device preference was rewritten as an objective improvement, and uncertainty cues were weakened in two summaries.
  • Exact quotations and typed values verify provenance and shape, not semantic entailment. The final device run contains accepted semantic errors.
  • Progress eligibility does not establish that the participant's current request has been answered or that ending is appropriate; the policy decides.
  • Revalidating a dependent after a prerequisite correction conservatively requires evidence from the correction turn or later, which may require extra confirmation.
  • These are nine fixed fictional user turns in four development fixtures. They are not adaptive user simulation, a held-out benchmark, human preference evaluation, or evidence of a quality improvement.
  • Prompts and contracts were adjusted using these fixtures. All earlier attempts and their additional costs remain separate; no SFT, DPO or RL was performed.
